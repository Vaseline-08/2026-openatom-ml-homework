# 说明：提示词设计思路 + 一次观察到的模型错误或局限

## 一、提示词设计思路

1. **先定角色，再定格式**：开头一句"你是一个校园信息助手"，把模型限定在"处理校园通知"的语境里，减少它主动扩展成通用问答的倾向；随后立刻给出三行模板，让模型知道"要填什么"。
2. **格式用"字段名 + 冒号"，不用自然语言描述格式**：直接给出 `一句话总结：/关键信息：/待办事项：` 的空模板，模型照着填即可，比写"请分三点回答、第一点总结……"更不容易跑偏。
3. **约束条件要具体、可检查**：写成"只依据用户提供的文本，不要编造原文中没有的信息""没有时间、地点或截止日期时写'未提及'""没有明确任务时写'无明确待办'"，每条都能在输出里被一眼验证；这比笼统的"不要胡说"有效得多。
4. **明确禁止加料**："不要添加任何额外说明"是为了防止模型在三个字段之外再写客套话或补充建议，破坏可解析性。
5. **低温度**：`temperature=0.3`，让同类输入的回答更一致，减少措辞漂移。
6. **保持对照组只差一个变量**：`text_prompt.py` 与 `main.py` 的代码、参数、模型完全相同，只把 `SYSTEM_PROMPT` 换成"总结以下通知"，这样两次输出的差异才能归因到提示词本身。

## 二、一次观察到的模型错误或局限

**观察到的现象（技术问题那一类输入）**：
把"Python 中列表和元组有什么区别？什么时候应该使用元组？"这类**知识性问题**喂给"校园通知总结"的固定模板时：

- **加强提示词版**（`任务二_技术问题.png`）：模型虽然保持了格式，但把知识问答硬塞进通知模板——"待办事项：无明确待办"，"关键信息"里列的是列表/元组的区别。格式是保住了，**语义上却是错位的**：这个模板本来是为"通知"设计的，不适用于"问题"。
- **简单提示词版**（`任务三_弱提示词_技术问题_1/2.png`）：模型直接输出了一整篇 Markdown，篇幅远超"总结"，说明**简单提示词无法约束输出长度与形态**。

**这暴露的局限**：固定输出格式是一把双刃剑——它换来稳定性，但也会**迫使模型把不适配的输入强行塞进模板**；而放宽格式又会立刻失去可控性。实践中应根据输入类型分流（例如先判断输入是"通知"还是"提问"，再套用不同提示词），或者用结构化输出（JSON）+ 程序侧校验来兼顾两者。
